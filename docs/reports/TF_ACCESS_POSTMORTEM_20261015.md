## 2. 技术结论与限制

**没有定位到某一行修改是失效的唯一原因。** 最近修改后仍有成功读目录的记录，随后在没有记录到新固件修改的上电周期失败。因此不能把“改几个代码直接造成故障”写成已证实因果，也不能借此排除软件因素。

新环境恢复支持继续采用该初始化路径，但 SDK、CPU、PSRAM、启动流程以及期间重新接线构成混杂变量；没有固定全部其他条件的新旧版本 A/B。两次冷启动与反复读取也不等于写入、全卡或长期验收。

主控异常身份、容量和原始扇区结果不能由单纯文件系统损坏解释全部现象。卡座去耦、接触、电源瞬态、卡片状态和驱动兼容性仍未充分排除。9 月的丢失簇机制与本次初始化异常必须分别记录，不能混为同一根因。

## 3. 确认的工程问题

| 问题 | 风险与责任 | 预防措施 |
|---|---|---|
| 无 Git 历史与版本绑定 | 无法可靠比较、二分或还原每轮改动 | 初始快照、任务分支、单一目的提交、验收绑定提交/产物 |
| 默认旧业务入口与正常诊断程序并存 | 默认上传可能覆盖当前可用程序 | 明确入口，阻止隐式上传，写设备另设批准门槛 |
| 共享诊断源码和外部复制目录 | 实际构建输入可能漂移 | 冻结自包含输入；独立构建输出，不覆盖正常产物 |
| 正常产物仅在构建缓存中 | 清理/重建可能丢失回退材料 | 独立基线、文件哈希、备份位置和恢复限制 |
| 状态、旧目标和旧记忆交叉 | 容易把历史通过或目标当成当前能力 | 状态、计划、流程唯一入口，历史归档并标注适用性 |
| 归因与验收边界表述过强 | 可能误导后续排查与变更 | 区分观察与假设；复位和断电分开；无证据不宣称通过 |

本次整改承担变更控制与证据管理责任，不虚构已经找到的技术根因。现有资料不能还原的部分明确保留未知。
