## 内存与发送路径证据

启动日志显示真实采集池常驻申请 101376 字节。`recorder.cpp::cleanup` 保留此池；合成试验未使用真实采集池。MIRROR 的 `rate190_stream.cpp::session` 额外分配 25600 字节内部队列，`rate240_tf.cpp::BufferClaim` 又分配含 FIL、2400 字节数据和 4096 字节读缓冲的工作区。PSRAM 在固定 SDK 中关闭，WiFi 使用动态收发缓冲。

并发 session_start 内部空闲堆为 53460，最大连续块 31744；这条日志位于网络队列分配之前。仅扣除网络队列即剩约 27860，再扣工作区以及分配器开销后，网络动态分配余量显著收窄。两处准入各保留 16384 字节，尚无证据证明这一预算足以覆盖 WiFi/lwIP 峰值。

关闭会话并释放网络队列后的 free=35388、largest=23552，历史最低汇总从 21184 降到 640。固定 SDK 的 `heap_caps.c::heap_caps_get_minimum_free_size` 累加各 heap 独立历史最低值；640 是历史统计汇总，故障瞬间的总空闲量和实际分配失败仍需额外证据。此前对话中“内部堆最低余量”的描述按此统计含义理解。

固定 lwIP 的 `api_msg.c::lwip_netconn_do_writemore` 在发送缓冲不足或 `tcp_write` 返回 ERR_MEM 时等待 ACK/轮询继续；超过发送期限且已有部分写入时可返回部分字节数。故本轮 `errno=0` 与 768 字节返回值覆盖了多种底层原因。当前证据支持优先检查内部内存压力与发送缓冲回收，尚未记录实际失败分配或 TCP ACK/重传/窗口。
