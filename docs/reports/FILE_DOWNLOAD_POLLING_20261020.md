# HTTP文件下载任务轮询等待对照

2026-10-20，实施前源码`862eff50d66c98c24b1646fa79f96d524aecd962`。
依据[文件路径限制分析](AP_FILE_TRANSFER_LIMITS_20261020.md)，本次服务端只将
`file_download.cpp::waitFile`每次查询任务状态前的固定等待由10ms改为5ms。
客户端轮询调整由另一agent单独实施，不把两者的作用混称为单变量实机结论。

保持每个任务6秒deadline、job匹配检查、变更POST不重放、2048字节块、base64/
JSON路径和主任务5ms循环。未改SDK、PSRAM、任务优先级、异步架构、文件所有权、
取消隔离、完整性及完成发布条件。未增加HTTP请求的并发度，每次等待仍让出任务。

1MiB含512个2048字节数据块；仅每块固定等待的算术成本由约5.12s减到约2.56s，
另有begin/EOF、调度、网络发送和摘要成本。这不是预测完整文件提速比例，也不
保证节省2.56s；查询更频繁还可能增加cJSON分配和主控负担，须后续实测。

本轮核实实际diff仅这一等待值；没有现成编译实际`file_download.cpp`的宿主测试，
不为这一可逆延迟改动新增镜像常量测试，不把其他文件路由host检查说成此handler
已执行。本轮未运行新测速、未连接设备、未烧录或构建整套固件。

最终检查由新候选实际固件编译及直连AP传输承担：新建验收目录中的1MiB文件，
完整长度/SHA-256、重复同尺寸总耗时、任务释放及失败/取消不发布完整文件。源码、
镜像、桌面产物和网络条件须绑定。旧fb固件约98kB/s下载记录不覆盖本次版本，
也不能作为本次速度结论；未取得新实测前只称等待策略变更。
