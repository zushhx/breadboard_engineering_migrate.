   Flash: [===       ]  26.9% (used 899657 bytes from 3342336 bytes)

   Flash 从加 UI 前的 11.4% 涨到 26.8%，多出来的约 500 KB 里，内嵌网页只占 **45 KB**（其余是 WiFi 协议栈 + lwIP + 我们自己的 SHA-1/HTTP/WebSocket 代码）。

   工具链：PlatformIO 6.2.0 + espressif32@7.1.3 + framework-arduinoespressif32 **4.20017（= Arduino-ESP32 2.0.17）**。
   产物：`.pio/build/breadboard/firmware.bin` + `bootloader.bin` + `partitions.bin`。

   编译暴露并已修掉的笔误（代码里都留了注释）：

   | 错误 | 原因 | 修法 |
   |---|---|---|
   | `PIN_CTRL` 重定义 | 与 ESP-IDF 的 IO MUX 宏撞名 | 改名 `REG_PIN_CTRL` |
   | `INA226 ina` 与 `namespace ina` 冲突 | 变量名撞命名空间 | 变量改名 `powerMon` |
   | `SD_MMC::begin()` 无匹配函数 | 按 3.x 的 10 参数写法调用，而本框架是 2.0.17，应「先 `setPins` 再 `begin`(5 参数)」 | 改为 `setPins` + `begin`，频率单位 kHz |
   | **包络累加器溢出** | `disp.h` 里把 min/max 窗口初值 `±100000.0f` 存进 `int16_t` → 被截断成乱值，波形会整体错 | 声明改为 `float`。**这条是靠编译警告 `overflow in conversion from 'float' to 'int16_t'` 抓出来的** —— 所以每次编译都别忽略警告 |

2. **寄存器来源已逐条核实，不靠记忆：**
   - IIS3DWB 寄存器地址表 ← DS12569 **Rev 8** Table 7（官方原件，2026-09-18 下载核对）
   - IIS3DWB 初始化序列 ← ST 应用笔记 AN5444（`INT1_CTRL=0x01` → `CTRL6_C=0x00` → `CTRL1_XL=0xA0`）
   - `WHO_AM_I` = **`0x7B`**（DS12569 默认值 `01111011b`）。**注意：0x63 是错的**，此前资料里的 0x63 已全线更正。
   - INA226 寄存器与位域 ← TI SBOS547
   - 寄存器地址：CTRL1_XL=0x10、CTRL3_C=0x12。DS12569 Rev8 §3.1 支持 SPI Mode 0 和 3；本工程采用 Mode 3，不能将 Mode 0 本身视为错误。

3. **三处关键值已对照 DS12569 Rev 8 官方原件核实完毕**（2026-09-18，下载原件逐条核对，非二手转述）：

   | 项 | 核实结果 | 出处 |
   |---|---|---|
   | `STATUS_REG` 的 `XLDA` 位 | **bit0**（位序 bit7→bit0 = `0,0,0,0,0,TDA,0,XLDA`）。原代码就是 bit0，**无需修改** | Rev 8 §9.21 Table D2/D3 |
   | 片内温度换算 | **T(°C) = 25 + raw/256**（25 °C 时输出 0 LSB；灵敏度 256 LSB/°C；刷新 104 Hz；失调 ±15 °C） | Rev 8 §2.3 温度特性 |
   | ±2g 灵敏度 | **0.061 mg/LSB**（±2%）；另 ±4g = 0.122、±8g = 0.244、±16g = 0.488 | Rev 8 Table 3 机械特性 |

   **结论：三处原代码都是对的。** 本轮只补全了常量与出处注释，没改逻辑。顺带补了两个可选能力：
   - `IIS3DWB::temperatureReady()` —— 用 `STATUS_REG.TDA`(bit2) 判断温度数据就绪
   - `IIS3DWB::setAxisMode(sel)` —— 切单轴模式，噪声密度从 **75 → 60 µg/√Hz**（只关心单一方向时有用）

   到货后先做静置正反方向对照（DS12569 Rev8 §2.6.1～2.6.2）：同一轴沿重力方向正、反放置，分别记录 `a+`、`a−`。零偏估计为 `(a+ + a−)/2`；读数以 g 为单位时，按 1g 换算的标度比为 `|a+ − a−|/2`。应核对两次姿态和稳定性，单次合模量偏离 1g 不能直接视为灵敏度误差或据此修改系数。

   2026-10-14 诊断版新增串口 `j`，实时读取身份与配置；`k` 只输出静置统计。`tools/capture_iis3dwb_readonly.py` 自动保存三轮 j/v/k 日志，身份或配置不符、数据缺失或样本不足时停止。它不复位主控、不修改系数、不发送录制或写卡命令；换姿态后用 `--pose-label` 记录实际放置方式。

   串口 `u` 实时读取 INA226 身份、CONFIG、CAL；本工程初始化期望为 CONFIG=0x4527、CAL=2048。`tools/capture_ina226_readonly.py` 每约 2 秒保存一次快照，异常时停止并保留状态，不自动复位或补写校准。`c` 在 CAL 无效时停止电流/功率数值输出。保持测试期间应固定接线；拔插或改线后重新初始化并开启新一轮记录。

## 四、无线 UI（浏览器界面）

**这是什么**：设备自己开一个 WiFi 热点，里面跑 HTTP + WebSocket 服务器；手机或电脑连上去，浏览器打开 `http://192.168.4.1/`，就能看到**电量 / 无线充状态 / 实时振动波形 / 三轴 RMS 与峰值 / TF 卡写入进度**。

**为什么不做"自带屏幕"**：本路线采购清单里没有任何显示屏；而振动监测这个场景，人本来也不会盯着刀柄看——手机上看更合理。以后想加屏（如 1.3" TFT）属于另一个模块，随时可加。

### 4.1 怎么用

1. 设备上电 → 串口会打印热点名与密码：
   ```
   热点 VibMon-A3F2   密码 vibmon2026   浏览器打开 http://192.168.4.1/
   ```
2. 手机/电脑连这个热点 —— **不需要外网，也不需要实验室路由器**（车间/实验室的 WiFi 常要认证，自己发热点最省事）
3. 浏览器开 `http://192.168.4.1/`
4. 「开始采集」= 开始写 TF 卡；**不采集时波形照样实时刷新**，方便先找工况再决定录哪一段

> 串口命令 `n` 可关掉 WiFi。采集时若发现丢帧，先关它对比 —— WiFi 发射峰值 355 mA 是设备里最大的干扰源。关掉后 UI 暂时不可用，**断电重启即恢复**。

### 4.2 界面上每一块数据从哪来

| 显示项 | 来源 | 说明 |
|---|---|---|
| 电量 | 电池 + → 10k/10k 分压 → **IO4（ADC1_CH3）** | 开路电压法估算，见 4.4 的误差说明 |
| 无线充状态 | Qi 模块 5V 输出（**SS34 之前**）→ 10k/10k 分压 → **IO5（ADC1_CH4）** | 见下方"为什么不能直接量 5V 轨" |
| 5V 轨电压/电流/功率 | INA226（I²C） | 原有模块，无需新增 |
| 实时波形 / RMS / 峰值 | IIS3DWB → 抽帧流水线 → WebSocket | 见 4.3 |
| TF 卡进度 / 文件名 | Recorder 统计 | 已有 |

**★ 为什么 Qi 检测必须单独引一路，不能直接量 5V 轨**

系统 5V 轨上，USB（经 D1）和 Qi 输出（经 SS34）是**"二极管或"**关系，两者叠加在同一条轨上。量这条轨的电压，USB 和无线充看起来**一模一样，分不出是谁在供电**。所以 Qi 那一路必须取在**它自己模块的输出端、SS34 之前**：有 Qi 读回约 5 V，没 Qi 读 0 V，判定干净利落。

**⚠ 为什么电量 / Qi 检测只能落在 IO4、IO5**

ESP32-S3 有 ADC1（GPIO1~10）和 ADC2（GPIO11~20）两组。**ADC2 与 WiFi 射频共用硬件，WiFi 一激活 ADC2 就读不出值**（Espressif 官方 FAQ 原文："ADC2 与 Wi-Fi 共用资源，Wi-Fi 激活期间不可读取"）。本方案 UI 必须常开 WiFi，所以模拟量只能落在 ADC1；而 ADC1 里 GPIO9/10 被传感器 SPI 占了、GPIO2 是 LED、GPIO3 是 strapping 脚 —— 干净的只剩 **IO4 和 IO5**。

接线（两路一样，共 4 只 10k 电阻 + 2 只 100nF）：

```
被测点 ──[10k]──┬──[10k]── GND
                └── 100nF ── GND
                └── ADC 引脚
```

分压比 2.0，节点源阻抗 10k∥10k = 5 kΩ。电池 4.20 V → 2.10 V，Qi 5.25 V → 2.63 V，都在 ADC 量程内。

### 4.3 "被处理过的、不大的"实时信号是怎么来的

原始 26.667 kHz 直接上网是 **160 KB/s**，会把 WiFi 和界面一起压垮。所以设备端做三步处理：

| 步骤 | 做法 | 为什么这么做 |
|---|---|---|
| ① 去直流 | 用 3 秒一阶低通估出重力/零点 DC，信号减掉它 | 静置时 Z 轴显示 **0 g** 而不是 1 g，振动幅度一眼可见 |
| ② min/max 包络抽帧 | 每 26 个原始样本压成 1 个点，**同时记住这 26 个里的最小值和最大值** | 冲击/崩刃是窄脉冲，**隔点抽样会整段抽没**；min/max 包络一个峰值都不丢 |
| ③ RMS / 峰值 | 在**全速原始样本**上求均方，不是抽帧后算 | 保证有效值是真实振动有效值 |

**带宽账**：26667 ÷ 26 = **1026 Hz** → 32 点/帧 → **约 32 fps** → 每帧 398 B → **12.7 KB/s**（相对 160 KB/s 压了约 **12.6 倍**）。

**关键性质：显示与存储互不干扰。** 采集在 core 1、写卡在 core 0 的独立任务，中间隔着 192 KB PSRAM 环形缓冲。WiFi 就算卡一下，丢的也只是显示帧，**SD 卡里的原始数据一帧不受影响**。

> 界面右上角「分量」可切换 **交流（去直流）/ 直流（含重力）**。切直流时前端把设备上报的 DC 值加回去，看到的就是未处理量——用于确认信号本身合理。

### 4.4 电量估算的诚实边界

用**开路电压法**，没有库仑计。原因：原设计的 INA226 分流串在**系统总回路**上，测的是系统总电流，不是电池电流。

- 锂电 3.7~3.9 V 是**平台区**，一小段电压覆盖大半容量 → 平台区误差可达 **±15%**
- 带负载时内阻压降会让读数偏低 → 大电流时电量会"掉一格"

固件据此做了两处缓解：**只在系统电流 < 300 mA 时才更新 SOC**，且每次最多变动 1%。要精确必须加库仑计（BQ27441 / MAX17048），属后续升级项。

### 4.5 WebSocket 帧格式（想自己写上位机时看这里）

UI 与设备之间是**二进制帧**（不是 JSON，省带宽也省解析）。波形帧全部小端：

| 偏移 | 类型 | 内容 |
|---|---|---|
| 0 | u8 | 魔数 `0xAA` |
| 1 | u8 | 类型 `0x01` = 波形帧 |
| 2 | u16 | seq 帧序号（**跳号 = 丢帧**） |
| 4 | u32 | 设备毫秒 |
| 8 | u16 | 抽帧后等效速率（1026） |
| 10 | u8 | 抽帧比（26） |
| 11 | u8 | 轴数（固定 3） |
| 12 | u16 | 点数 nPts |
| 14 | … | 逐点 → 逐轴 → (min, max)，各 int16 小端 |

单位换算：`g = 原始值 × 0.061 / 1000`（`SENS_MG_PER_LSB` = 0.061 mg/LSB @FS=±2g）。

另有 **2 Hz 的文本 JSON 状态帧**，字段见 `src/main.cpp` 的 `buildStatusJson()`。
UI → 设备命令（文本 JSON）：`{"c":"start","s":90}`、`{"c":"stop"}`、`{"c":"zero"}`、`{"c":"list"}`、`{"c":"self"}`、`{"c":"wifi","on":0}`

### 4.6 改界面

| 场景 | 做法 |
|---|---|
| 只是想看界面长什么样 | 直接**双击 `webui/index.html`** —— 会**自动进入演示模式**，用合成振动数据驱动，完全不需要硬件 |
| 改了 UI 要烧进固件 | `python tools/build_webui.py` 重新生成 `include/webui_asset.h`，再 `pio run` |
| 想边改边看不重编译 | 把 `index.html` 拷到 **TF 卡根目录并改名 `ui.html`** —— 设备会优先用卡上这份 |
| 改完想确认没改坏 | `node tools/ui_selftest.js` —— **不需要硬件也不需要浏览器**，28 项断言全过才退出码 0 |
| 想强制指定数据源 | URL 加参数：`?demo=1` 强制演示 / `?live=1` 强制连设备（即使在本地文件下） |

**数据源是怎么自动判断的**（很关键，避免把合成数据当真机数据看）：

| 情形 | 行为 |
|---|---|
| A. `file://` 本地打开 | 直接进演示模式 |
| B. 从设备打开，但**从未连上过** WebSocket | 3 秒后自动兜底进演示模式（例如在 IDE 预览面板里看这个页面） |
| C. **连上过之后**又断了 | **只重试，绝不切演示** —— 否则会用假数据冒充真机数据，那比报错更危险 |

演示模式下的状态点与提示文字都是橙色并写明"合成数据"，不会与真机状态混淆。

> `ui_selftest.js` 会把 `index.html` 的内联脚本抠出来，在 Node 里配一套最小 DOM 桩跑起来，然后核对四件事：渲染循环连跑 400 帧不抛异常、环形缓冲索引不越界、**WebSocket 二进制帧解码与设备端序列化逐字节对得上**、演示模式统计量的**量纲**是 mg（不是 g）。
> 这不是形式主义 —— 本轮 UI 的两处真 bug（演示波形点数少 26 倍、RMS 单位差 1000 倍）都是它抓出来的，两个在浏览器里都「看起来能跑」。

### 4.7 为什么没用第三方 WebSocket 库

握手 / SHA-1 / base64 / 帧编解码**全部自包含**（`src/netui.cpp`），**零外部库依赖**。理由：少一个构建期依赖就少一处下载失败或版本不兼容的风险，而本项目只需要 RFC6455 的最小子集（握手 + 收发小帧）。

### 4.8 功耗与稳定性：把账算清楚

这一节回答一个很自然的疑问：「实时传输是不是又耗电又不稳？」

**先给结论：耗电确实增加，但大头不是"传数据"，而是"电台开着"；稳定性真正的风险在供电和共存，不在传输本身。**

#### 电流从哪来（ESP32-S3-WROOM-1 数据手册 Table 12/13/14 实测值）

| 状态 | 电流 |
|---|---|
| 电台关（Modem-sleep @240 MHz，双核在跑） | **33 ~ 108 mA** |
| 保持关联（以 RX 95 mA 为主） | **+95 mA** 左右 |
| TX 峰值（11b 1 Mbps @20.5 dBm） | **355 mA**（瞬时） |
| TX（11g 54 Mbps @18 dBm） | 297 mA |

加上 TF 卡写入（30~100 mA）、IIS3DWB 1.1 mA，系统账大致是：

| 工况 | 平均电流 | 2000 mAh 电池理论续航 |
|---|---|---|
| WiFi 关，纯采集写卡 | ≈ 110 mA | ≈ 18 h |
| WiFi 常开 + 32 fps 推流 | ≈ 210 mA | ≈ **9.5 h** |

**续航大致砍半** —— 是真的，但不夸张。

#### ★ 关键认知：12.7 KB/s 的数据本身几乎不耗电

| 空口速率 | 每帧（≈500 B 含 MAC/ACK 开销）占用 | 32 fps 下的空口占比 |
|---|---|---|
| 54 Mbps（11g，正常情况） | ≈ 150 µs | **0.5 %** |
| 1 Mbps（11b，最坏被压到基础速率） | ≈ 5 ms | 16 % |

**平均只多花 2~10 mA。** 由此推出一条反直觉的结论：

> **把帧率从 32 fps 降到 8 fps 只省 1~2 mA，不值得做。** 要省电只能整个把电台关掉。

所以固件里**没有**做"降帧率省电"这种没收益的优化。

#### 稳定性要分三层看

| 层次 | 判断 | 依据 |
|---|---|---|
| **传输层** | **其实很稳** | 12.7 KB/s 相对空口能力是九牛一毛，几乎不会拥塞/丢包 |
| **供电层** | **有真风险** | TX 峰值 355 mA + TF 写 100 mA vs ME6217 热限流 **588 mA**，余量约 20%。而且这是**热**限流，压差越大越紧 |
| **共存层** | **有真风险，但后果被误解了** | WiFi 中断与写卡任务都抢 core 0 → 真正的后果是「**写卡丢样本**」，不是「波形传不出去」 |

**显示链路与存储链路是物理解耦的**（192 KB PSRAM 环形缓冲）：WiFi 抖动丢的只是显示帧，UI 上有 seq 跳号统计；**SD 卡里的原始数据一帧不受影响**。

#### 供电上要做的三件事（按重要性）

1. **3V3 轨并 100~470 µF 电解电容** —— TX 突发 355 mA 会在 3V3 上造成几十 mV 跌落，这是最容易踩的坑
2. 保持磁珠做 3V3_SENS 分轨，别让射频噪声串到传感器
3. 发射功率已压到 **11 dBm**（10 m 内完全够用）

### 4.9 排障手段：录制时关掉 WiFi

> **定位（2026-09-18 已定）：这是排障工具，不是常规工况。**
> 本版的正常用法就是「实时显示 + 写 SD 卡**同时**跑」，见 §4.11 —— 二者从来不冲突。
> 只有「写入丢帧」持续不为 0 时才开它，用来定位干扰来源。**默认关闭。**

既然"省电只能靠关电台"（见 §4.8），而关电台又确实能去掉射频与电流干扰，那就把它做成一个开关备着。

界面上在「设备诊断」卡片里（按钮名「排障 · 录制时关 WiFi」），或串口命令 `m`。打开后：

| 阶段 | 行为 |
|---|---|
| 录制开始 | 先把手上的 ack / 状态帧发出去（延迟 `REC_WIFI_OFF_DELAY_MS` = 500 ms），然后 `WiFi.mode(WIFI_OFF)` **电台彻底断电** |
| 录制期间 | UI 提示「设备静默录制中（WiFi 已关闭，录完自动恢复）…」并持续重连，**不会谎报成故障** |
| 录制结束 | 自动重新开热点，浏览器 2 秒内自动连回来 |

**换来什么**：① 去掉射频对 26.667 kHz 采集的干扰；② 去掉 TX 355 mA 峰值电流对 LDO 的压力。
**代价**：录制期间看不到波形（反正那段时间也不该分心看波形）。

> ⚠ 这个开关与"连续推流看波形"是**两个工况**，不能叠加 —— 这正是它的意义所在。

### 4.10 从浏览器直接下载原始数据

录完之后不用拔 SD 卡：

```
http://192.168.4.1/dl?f=vib_00001.bin
```

界面上「列出卡内文件」会把卡上所有 `vib_*.bin` 列出来，每行一个「⬇ 下载原始数据」链接，点一下浏览器原生下载（带进度条，因为响应头里有 `Content-Length`）。

**三条安全约束（都必要，别删）**：

1. **采集中一律拒绝（HTTP 409）** —— 下载要读 SD，而写卡任务正在另一个核上写 SD，两个任务并发碰同一套 SDMMC 驱动会出问题。所以界面上采集中根本不给下载链接。
2. **文件名白名单** —— 只放行 `vib_*.bin`、且只允许 `[A-Za-z0-9._-]`。否则这就是个"把整张卡暴露成公网文件服务"的洞。
3. **流式发送带 2 秒无进展保护 + `vTaskDelay(1)`** —— 对端掉线时不能把 netTask 永久卡死，也不能饿死同核的写卡任务。

### 4.11 这一版的正常工况，以及下一板的供电瓶颈（重要，涉及改板）

#### 正常工况：实时显示与写 SD 卡**同时**进行，不是二选一

这两件事从来不冲突 —— 固件本来就是按两条独立链路做的：

| 链路 | 路径 | 何时在跑 |
|---|---|---|
| 原始数据 → TF 卡 | core 1 采集 → PSRAM 环形缓冲 → core 0 `writerTask` | 采集期间 |
| 处理后的波形 → 浏览器 | core 1 抽帧 → core 0 `netTask` → WebSocket | UI 开着就一直跑 |

按「开始采集」之后就是**又看波形又写卡**。
§4.9 的「录制时关 WiFi」只是**排障手段**：只有当「写入丢帧」持续不为 0 时，才开它来定位是不是射频/电流干扰。

#### ⚠ 下一板：不要指望"加大无线充功率"解决供电余量

**症结不在输入端能送多少功率，而在 3.3 V 这一级怎么把电降下来。**

按 LDO 输入 5.0 V 算（电流取自 ESP32-S3 手册 Modem-sleep 表 + RX 95 mA + TF 卡典型写入电流，**属估算，到货必须实测**）：

| 工况 | 3.3V 侧电流 | LDO 自身耗散 | 从 5V 轨取电 |
|---|---|---|---|
| 只推流（WiFi 开、不写卡） | ≈ 190 mA | (5.0−3.3) × 0.19 = **约 320 mW** | ≈ 0.95 W |
| 推流 **+ 写 SD 卡** | ≈ 230 mA | (5.0−3.3) × 0.23 = **约 390 mW** | ≈ 1.15 W |
| **写卡带来的增量** | +40 mA | **+约 70 mW（+22%）** | — |
| 当前 Qi 接收模块能力（5 W，5V/1A） | — | — | **5 W** |

→ **输入端有 4 倍以上余量，从来不是瓶颈。**

→ **输入端已有约 4.8 倍余量。** 加大无线充功率提高的是"能送多少"，而 LDO 的发热只取决于**它自己两端的压差 × 输出电流**，与输入功率无关。**把 5 W 换成 15 W，LDO 该多热还是多热。**

⚠ 更要小心**反效果**：Qi EPP（15 W）的接收端输出是 **9 V / 12 V**，不是 5 V。若沿用 LDO 去做 9 V → 3.3 V：
`(9 − 3.3) V × 210 mA = 1.2 W` —— SOT-23-5 根本扛不住，必然热关断（ME6217 热关断点 160 °C）。
**功率加大 + 沿用 LDO = 更糟，不是更好。**

#### ⚠ 先撤回一处表述（2026-09-18 用户追问后修正）

此前把「① 换 buck」写成"下一版的事"。**这个说法不准确：**

- **板载 LDO 换不掉** —— ME6217C33M5G 是焊在立创开发板上的 SOT-23-5，要"替换"它等于拆焊飞线，属改板，不该在面包板阶段做。
- **但根本不需要替换它** —— 你可以让它**不工作**，或者让它**几乎不工作**。这两条路**现在就能做**。

所以正确说法是：**"换 buck"现在做不到；但"用外置 buck 给板载 LDO 旁路/减负"现在就能做。**

#### 三个改法，治的是两类不同的问题（不能互相替代）

| # | 做法 | 治什么 | LDO 耗散（推流+写卡） | 现在能做吗 | 成本 / 代价 |
|---|---|---|---|---|---|
| **③ 加固去耦** | 3V3 轨并 **≥470 µF 低 ESR** + 100 nF，磁珠 3V3_SENS 分轨 | **瞬态**：TX 突发 355 mA 造成的几十 mV 跌落 → 传感器复位 / TF 卡掉卡 | 390 mW（不变） | ✅ **能** | ¥1，5 分钟，零风险 |
| **④ buck 降到 3.8 V 喂 5V 脚** | 5V → buck → **3.8 V** → 开发板 **5V 脚**（板载 LDO 照常工作，只是压差只剩 0.5 V） | **稳态**：平均耗散 | (3.8−3.3)×0.23 = **约 115 mW** | ✅ **能** | ¥2~5，改一根杜邦线；⚠ 此期间**不能插 USB** |
| **① buck 到 3.3 V 喂 3V3 脚** | 5V → buck → **3.3 V** → 开发板 **3V3 脚**（板载 LDO 完全不工作） | **稳态**：平均耗散 | **0 mW** | ⚠ 能，但**需先确认反灌安全** | ¥2~5；⚠ 要先实测"板载 LDO 输出端被外部灌 3.3 V"是否安全 |
| ② 电池直出 + buck-boost | 单节锂电 3.0~4.2 V → 3.3 V（原设计 TPS63031 就是干这个） | 稳态 + 电池低压失压 | 0 mW | ❌ 需改板 | 下一版 |

**为什么 ③ 和 ①/④ 都要做 —— 它们治的是两个不同的问题：**

- **③ 治瞬态跌落**（µs~ms 级毛刺）：电容就是干这个的。buck 的环路带宽跟不上一瞬间 355 mA 的电流跳变，所以**换成 buck 也照样需要这颗大电容**。
- **①/④ 治稳态温升**（分钟级平均耗散）：电容对此毫无帮助 —— 它只能把热量摊平，不能减少产热。

所以不存在"做了①就不用③"，反过来也一样。而 ③ 是**零成本零风险**的，没有任何理由不先做。

#### 器件（已核实，含立创编号）

- **MP1584EN** —— 立创 **C454188**（MPS 芯源，SOIC-8-EP）。输入 **4.5~28 V**、输出可调 **0.8~25 V**、**3 A**、开关频率 100 kHz~1.5 MHz、**非同步**降压。另有 MP1584EN-LF-Z = **C15051**。
- ⚠ 按已核实规律：**立创只有芯片，成品可调降压模块要走淘宝**（约 ¥2~5，21×16 mm，电位器调压）。芯片路线要配转接板 + 电感 + 反馈电阻，面包板阶段不划算 → **直接买成品模块**。
- 调压：模块空载接万用表，拧电位器到 **3.80 V**（走 ④ 那条路时）。
  为什么是 3.8 V 而不是 3.6 V：LDO 压差 **180 mV@300 mA** 且随电流上升，3.8 V 留了约 350 mV 余量。

#### 关于「v1 先不写 SD 卡」这个取舍（我的反对意见）

写卡给 LDO 增加的热负担只有 **约 70 mW（+22%）**，换来的是能不能验证 **M4 存储** —— 而 `面包板样机_需求拆解与实施规划.html` 里 **M4 是 MVP 四项之一**，关键路径明写 `M2→M1→M3→M4→数据重放`。v1 若不写卡，M4 悬空、数据重放链路（`bin2csv.py` / `analyze.py`）也验不了，**MVP 定义就被打破了**。

而且**功能上写卡与推流从来不冲突**（两条独立链路），它们只共享同一个 LDO 的热预算。所以"v1 不写卡"省下的不是功能复杂度，只是那 70 mW。

→ **建议的两全做法**：默认「推流 + 写卡一起跑」；一旦实测 LDO 烫手，就临时打开已做好的**「排障 · 录制时关 WiFi」**把数据录下来验证 M4，之后切回实时。**用一个开关切换工况，不需要砍功能。**

#### ME6217C33M5G 的诚实边界（已核实）

立创 / 嘉立创 / 云汉芯城三处商品页口径一致：输出 **800 mA**（条件 VIN ≥ VOUT + 1.0 V）、压差 **180 mV@300 mA**、工作范围 **2 ~ 6.5 V**、热关断 **160 °C**、PSRR 65 dB@1 kHz。

**但这几个页面都没有 θJA / 最大功耗 PD 的实测值。** 此前资料里写的"功耗上限 1000 mW"**出处不明，不要拿它当设计依据**。SOT-23-5 在无散热铺铜的条件下真实 θJA 通常在 200~250 °C/W 量级，按 85 °C 环境算 PD 预算只有 **300 mW 上下** —— 比 1000 mW 紧得多，也正好解释了上面那 357 mW 为什么危险。

→ **到货后请实测**：采集 + 推流连跑 10 分钟，用手背碰一下 LDO 附近（或热电偶测）。烫手就说明余量不够 —— 先关 WiFi（串口 `n`）跑，同时安排改 buck。

## 六、数据格式与上位机分析

文件写在 TF 卡根目录，命名 `vib_00000.bin`、`vib_00001.bin` …（每段一个文件）。

**文件头 32 字节（小端）**

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 4 B | magic `"VIBB"` |
| 4 | 2 B | version = 1 |
| 6 | 4 B | sampleRateHz（当前 26667） |
| 10 | 4 B | startMillis |
| 14 | 2 B | bytesPerSample = 6 |
| 16 | 16 B | 保留区 —— **段结束时回填**，见下表 |

其后为原始样本流，每样本 6 字节：`X_L X_H Y_L Y_H Z_L Z_H`（int16 小端交错）。

**保留区（偏移 16，16 字节）—— 段关闭前回填，用来判断"这段数据可不可信"**

| 偏移 | 长度 | 内容 |
|---|---|---|
| 16 | 4 B | `dropSamples` —— 本段录制期间**环形缓冲满**而丢掉的样本数 |
| 20 | 4 B | `writtenSamples` —— 本段实际落盘的样本数 |
| 24 | 4 B | `writeFails` —— 本段**写文件失败**的次数（卡满 / 掉卡 / 坏块） |
| 28 | 4 B | `lostByWrite` —— 本段因写失败而丢掉的样本数 |

> `dropSamples` 与 `lostByWrite` 是两个不同的故障（采集端太快 vs 存储端出问题），必须分开记。
> 两个都是 0，这段数据才算完整。
>
> 版本号仍是 1 —— 头长度没变，按固定偏移 32 读样本的旧工具不受影响。

### 6.1 静置标定检查（到货后第一件事）

**原理**：传感器静止不动时，三轴合模量必然等于 1 g —— 因为它测的是 DC 加速度。
所以「|a| 与 1.0000 g 的偏差」就是**标度误差**，不需要任何激振设备就能验证。

**两种查法，任选其一：**

```bash
# ① 固件端：串口敲 k，静置几秒自动完成
k

# ② 上位机端：对一段静置采集数据加 --calib
python tools/analyze.py vib_00000.bin --calib
```

**判据**（出处：DS12569 Rev8 Table 3 —— @FS=±2g 灵敏度 0.061 mg/LSB，公差 ±2%）：

| 合模量偏差 | 判定 | 处理 |
|---|---|---|
| ≤ ±2% | ✅ 合格 | 直接用 |
| ±2% ~ ±5% | ⚠ 超规格 | 定性观察够用；要精确就按提示改 `SENS_MG_PER_LSB` |
| > ±5% | ❌ 偏差过大 | **先排查**（是否真静止 / 接线虚接 / 附近有磁铁），别急着改系数 |

两个入口都会直接给出**修正后的 `SENS_MG_PER_LSB` 数值**（= 原值 ÷ 合模量）。

> 已用合成数据双向验证：静置数据判 ✅（合模量 1.0000 g）；故意把灵敏度设成 0.070 时判 ❌（合模量 1.1476 g），且给出的修正值 **0.0610 正是正确值**。

**注意这只校验标度。零偏（0 g 电平）要用两点法**：同一轴朝上读 `a1`、朝下读 `a2`，则 `offset = (a1+a2)/2`。

## 九、已知限制与后续优化

| 项 | 现状 | 后续 |
|---|---|---|
| 缓冲策略 | 环形缓冲（192KB PSRAM）+ 双核解耦，已能吸收写卡抖动 | **再叠加传感器板载 FIFO（3KB）做二级缓冲**，可显著放宽对写卡实时性的要求。需先对照 DS12569 确认 `FIFO_CTRL2/4`、`COUNTER_BDR_REG1` 的位域 |

| 量程切换 | 固定 ±2g | 切削振动可能打满，需补 ±4/±8/±16g 切换（`CTRL1_XL[3:2]`） |

## 十、红线（与验收包一致）

1. **INA226 分流电阻保持模块自带的 0.1 Ω，不要拆焊**（2026-09-21 决定，理由见 `include/config.h` 的 INA226 段注释）。满量程 ±0.8192 A，对系统峰值约 456 mA 有 1.8 倍余量；且小电流精度反而优于 10 mΩ（110 mA 时失调误差 0.09% vs 0.91%）。⚠ 但**一旦实测电流超过约 800 mA（例如将来 Qi 那一路同时供设备+充电），读数会饱和在满量程** —— 那时必须换 10 mΩ，并同步把 `config.h` 的 `SHUNT_OHM` / `INA_MAX_CURRENT` 改为 `0.010f` / `8.192f`（**CAL 不用动，恒为 2048**，因为本驱动令 1 个电流 LSB 恰等于 1 个分流电压 LSB 2.5 µV）。
2. **3V3_SENS 必须经磁珠分轨。** 直连会让开关噪声直接调制进加速度信号，事后无法从数据里剥离。
3. **大电流路径必须飞线。** 面包板触点 10~50 mΩ/点，走触点会让 INA226 读数被触点压降污染。
4. **DIL24 脚位按丝印接，不按芯片脚号。** 接错电源可能烧掉评估板，且补货要走海外。
5. **验证期先关 WiFi。** 板载 ME6217C33M5G 在 5V→3.3V 压差下受 1000mW 功耗限制，实际只能给约 588mA；系统峰值需求约 456mA，余量仅约 20%。
