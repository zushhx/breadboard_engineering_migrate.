# 工程、Git 与发布流程

本项目操作流程。当前能力与连接状态见 [STATUS.md](STATUS.md)，任务目标见 [ROADMAP.md](ROADMAP.md)。

## 1. 开始任务

读取导航、状态、适用规则和任务计划；检查 `git status --short --branch`、当前 HEAD 和已有用户修改。方案写明目的、影响、验收和回退，确认后进入任务分支。初始化的首次现状快照是建立流程的必要例外，不能当成全部功能已通过。

分支采用 `chore/…`、`fix/…`、`feat/…`；`main` 保存经确认的工程版本。提交按目的拆分，目录迁移与内容修正、工具调整分别提交。保护用户修改，禁止擅自强推、破坏性清理或改写共享历史。

## 2. 修改与审查

- 修改共享配置、SDK、引脚、时钟、PSRAM、初始化、分区或数据路径时，先在任务中写明影响并安排对应回归。
- 提交前运行 `python3 tools/project_check.py --local`；干净检出或 CI 使用不带 `--local` 的检查。
- PR 写明改动、影响、验证命令与结果、未测项、候选产物、回退办法及需确认事项。已配置远端时在 PR 审查；远端暂不可用时保留本地差异与审查报告，不冒充已建立 PR。
- 使用可用的 Codex 审查；区分自行复核与独立审查，修复发现后复查相关范围。自动审查是否启用以实际仓库配置为准。
- 本地 hook 是辅助门槛，不能代替 GitHub 服务端保护或用户确认。现有套餐不能保护私有分支时，明确记录限制；本轮不购买服务。

## 3. 构建与硬件门槛

主入口见[固件 README](../面包板样机_固件/README.md)。冻结基线的正常产物保持不变；重建输出进入本地独立目录，编译时间等因素可能使新文件哈希不同。构建结果只能记为构建通过。

烧录前先准备：任务分支与干净提交、具体目标主控身份、候选固件及 SHA-256、工具链/接线版本、备份与恢复办法、已完成检查、实机验收步骤。用户明确确认候选试烧后，记录批准并执行。不得用目录整理、查询、构建或环境升级的授权替代烧录授权。

涉及 TF 访问的变更，至少验证两次完整断电启动、一次卡保持供电的主控复位，并检查容量、目录与既有文件重复哈希。断电需要真实切断所有供电，串口 RTS/EN 复位不能代替。写入功能另验写入、同步、关闭、重新读取和异常恢复；没有证据的项目保留未测试。

发现回归后保存日志与产物，停止叠加无关修改，按已确认恢复策略处理；回到正常版本不代表根因已经找到。

## 4. 合并与发布

完成差异审查、相应检查与必要实机验收，向用户提供具体结果，再单独取得 `main` 合并确认。合并后按版本建立发布标签，记录源码提交、工具链、产物哈希、适用接法、验收范围、已知问题和恢复位置。正式部署/烧录仍按其授权范围办理。

本机全局规则源仓库位于 `C:\Users\acer\.codex\engineering-policy`，全局生效文件位于 `C:\Users\acer\.codex\AGENTS.md`。项目不复制整份全局规则；全局规则修订在该独立仓库提交审查和部署，记录源提交、哈希及备份。

## 5. 回退与归档

目录迁移前后清单见 [MIGRATION.json](MIGRATION.json)，原始内容在初始提交或本地快照保存。恢复文件前核对当前修改与目标内容，使用明确文件恢复或反向迁移方案；不要直接对整个工作区执行破坏性 reset/clean。

主控原固件恢复步骤、备份范围和限制见[基线说明](../baselines/tf-readonly-20261015/README.md)。原始 Flash 可能包含 NVS 数据，按本地敏感备份保管；本轮没有测试恢复试烧。
